The inner query reads courier_status and adds a column rn. ROW_NUMBER() OVER (PARTITION BY courier_id ORDER BY updated_at DESC) restarts the numbering for each courier and numbers that courier's rows from the newest to the oldest, so the most recent row gets 1. The outer query keeps only rows with rn = 1, which is one row per courier, and ORDER BY courier_id sorts them. The window is wrapped in a subquery because a window function cannot be used directly in WHERE.

On this data it returns two rows. Courier 2 gives 'offline' at 18:00, which is clearly the latest. Courier 1 has two rows at 09:30, 'online' and 'busy', so it returns one of them. When I ran it in SQLite it returned 'online', but that is not guaranteed: with a tie in the ORDER BY the database may pick either row, and it can change with a different plan, a different engine or different data order.

The trap is that a tie makes the result non-deterministic. This matters in ML pipelines because a feature table that silently picks different rows on different runs breaks reproducibility. Adding a tiebreaker, ORDER BY updated_at DESC, id DESC, makes the choice stable, and with it I got 'busy' for courier 1. Whether that is the right row is a business question, but at least it is the same every time.
