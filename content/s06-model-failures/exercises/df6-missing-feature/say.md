When a feature is missing, the system has to make an explicit choice, not let the model see something accidental. For a single missing feature I fill it from a default that was computed on the training data, for example the median, and I treat only `None` or an absent key as missing, so a real zero stays a zero. I also record which features were filled, in the response and in a counter. For the case in the question, that counter is exactly what would have shown it: the fill rate of `courier_distance_km` would jump from near zero to one hundred percent, and an alert on that rate would fire within minutes. The risk of defaults is that they hide an outage, because the service keeps answering with plausible but worse scores. So I set a limit: if too many features are missing, or a critical one is, I fall back to a simpler rule or a baseline model, or return an error the caller can handle. The trade-off is availability against quality, and I would agree the thresholds with the product owner before the incident, not during it.
