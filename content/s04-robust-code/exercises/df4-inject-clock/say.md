The current time is an input to the function, even though it does not appear in the signature. If `allow()` calls `time.time()` itself, the answer depends on something the caller cannot control, so the same sequence of calls can give different results on different runs. With an injected `clock`, the production code passes `time.monotonic` and behaves the same as before, but a test passes a fake clock that I move by hand. That lets me test the exact boundary, for example that after one second a bucket with a refill rate of one token allows exactly one call and not two, without sleeping and without flakiness. I can also test the clock going backwards, which I could never trigger on demand with the real one. The same idea matters beyond tests: a backfill or a replay of old events must use the time of the event, not the time the job runs, or reruns give different results. The cost is one extra argument, and I accept it. I would not inject the clock into code where time is not part of the logic, for example a log line.
