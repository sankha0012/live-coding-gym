I would first list where the output could depend on something other than the input. The usual suspects are random sampling without a seed, the current time, sorting with ties, set iteration, parallel steps that finish in different order, and database queries without an ORDER BY. Then I write a test that runs the whole pipeline twice on the same input and compares the output exactly, or by a hash of the file. I also run it once with the input rows shuffled, because a pipeline that is only stable for one input order is depending on that order. If the test fails, I fix the cause: pass a seeded random generator in as an argument, inject the time, and add the id as a tie-breaker in every sort so ties have a defined order. I keep the seed in configuration and record it in the output. What the test does not prove is determinism across machines, library versions or hardware, because floating point results can differ slightly, so I pin the versions and compare with a tolerance where exact equality is not realistic.
