Line by line. The logger "orders" prints each record to stdout as the level followed by the message. Three orders: A-17 has qty "3", A-18 has "three", A-19 has None. Both process functions call int(order["qty"]). For A-17 it succeeds and returns 3 in both. For A-18, int("three") raises ValueError; for A-19, int(None) raises TypeError; both are caught. process_bad logs the fixed text "failed to parse quantity" and returns None. After the "--- bad ---" header the output has two identical lines, "ERROR failed to parse quantity", and then the list [3, None, None]. process_good logs the order id, the offending value (repr, so strings show their quotes) and the exception text: "ERROR failed to parse quantity order_id=A-18 qty='three' error=invalid literal for int() with base 10: 'three'" and "ERROR failed to parse quantity order_id=A-19 qty=None error=int() argument must be a string, a bytes-like object or a real number, not 'NoneType'", followed by the same list [3, None, None].

Answers. The bad lines say that something failed but not which order, which value or which exception; the good lines carry the three things you need to act: the identifier, the input and the reason. In production, a message like "failed to parse quantity" means a person has to guess which of millions of orders failed and why; you cannot search for it, count by cause, alert on a new kind of error, or replay the one record. The return values are the same because logging only observes the handling and does not change it; that is no problem for the program, but it is exactly why the bug is easy to miss: tests on the return value pass while the diagnostics are useless. Note that the example logs the value (qty), so in real systems you must also avoid logging secrets and personal data.

Trap: a log line you cannot act on. Defence: log the identifier, the input (redacted where needed), the exception and the decision taken, ideally as structured key=value or JSON fields.
