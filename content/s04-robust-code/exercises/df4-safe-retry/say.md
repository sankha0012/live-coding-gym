The teammate is right. A timeout only tells me that I did not get an answer, not that the server did nothing, so a blind retry of a charge can run it more than once. To make it safe I make the operation idempotent with an idempotency key. The client generates one key per logical charge, for example from the order id and the purpose, once, before the first attempt, and sends the same key on every retry. Generating a new key per attempt would defeat the purpose. The server stores the key together with the result of the first successful processing, and when it sees the same key again it returns the stored result and does not charge again. The check and the store have to be atomic, for instance a unique constraint on the key, or two parallel retries can both pass the check. I would still retry only transient errors such as timeouts and connection errors, never a validation error, and keep the keys for a limited time. What can still go wrong: if the same key is reused with a different amount, the server should reject it and not return the old result silently.
