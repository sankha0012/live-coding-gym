SERVER_LATENCY says the upstream service takes 45 seconds to answer. fake_get simulates an HTTP call: with timeout=None it just returns the answer and the time spent, 45.0; with a timeout smaller than the latency it raises TimeoutError. score_blocking passes no timeout, so it returns 0.9 after waiting 45.0 seconds: "blocking: score=0.9 waited=45.0s". score_with_timeout passes timeout=2.0, which is less than 45, so fake_get raises, the except branch returns the fallback score 0.5 and reports that it waited the timeout: "with timeout: score=0.5 waited=2.0s". The last two lines are arithmetic: 100 sequential blocking calls take 100 * 45.0 = 4500.0 seconds against a 100.0 second budget, while with the timeout the worst case is 100 * 2.0 = 200.0 seconds. Note that 200 is still above the budget, so a timeout alone does not complete the job in time; it bounds the damage.

Answers. Without a timeout the caller waits for as long as the slowest dependency chooses: here 45 seconds per call, and in real HTTP libraries often forever (the requests library has no default timeout). In production a stuck upstream then ties up threads, connections and workers until the caller itself is exhausted: one slow dependency turns into a cascading outage, health checks stop answering, and a batch job never finishes. The default score of 0.5 is a fallback: the request completes in bounded time with a neutral answer instead of failing. The price is quality and honesty: the user gets a non-personalised result, so the fallback must be logged and counted, otherwise a dead dependency is invisible; and you should pair it with a deadline for the whole batch and, for repeated failures, a circuit breaker.

Trap: an unbounded wait on a network call. Defence: always pass an explicit connect and read timeout, derive it from the latency budget, define a fallback, and record when it is used.
