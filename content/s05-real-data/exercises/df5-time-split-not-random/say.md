I trust my number, because it matches how the model is used. In production the model predicts orders that have not happened yet, so the test set must come after the training set. A random split mixes the periods: the model trains on orders from the same days and the same promotions as the test orders, so it effectively sees the future and the test error is optimistic. After launch the error rises because of drift, new restaurants and seasonality, and the offline number did not predict that. With a cutoff date, `train` is strictly before it and `test` is at or after it, so every row is on exactly one side. A fixed cutoff also makes the split deterministic, with no random seed to manage. The trade-off is that the test period may be unusual, for example a holiday, so I would also check a rolling series of cutoffs. For data without time structure, a random split is fine.
