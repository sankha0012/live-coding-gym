The script has four events. The shipped event for u1 has event time 110, earlier than paid at 130, but it arrives after it. The first loop writes status by arrival order, so the last arrival wins and u1 ends as "shipped". The second loop only accepts an event whose time is at least the latest time seen for that user. created (100) is accepted, paid (130) is accepted, shipped (110) is below 130 so it is counted as late and ignored, and u2 created is accepted. The output is the arrival result [('u1', 'shipped'), ('u2', 'created')], the event-time result [('u1', 'paid'), ('u2', 'created')] and "dropped as late: 1".

Answers. Arrival order is not event order. If events can arrive late, last-write-wins by arrival moves a user backwards in their lifecycle, here from paid back to shipped, and the state depends on network timing, so a replay can give a different answer. The event-time version compares timestamps and ignores the stale event. In production you would also log or count late events, and keep them for audit or a backfill, instead of dropping them silently. Trap: processing order treated as event order. Defence: compare event timestamps (and break ties deterministically).
