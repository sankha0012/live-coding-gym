The script has four update events for two users, listed out of time order. The first block calls drop_duplicates(subset="user", keep="last"). keep="last" keeps the last row in the current row order, not the latest timestamp. For ana that is the row dated 2026-03-01 ("free"), for bob the row dated 2026-03-04 ("pro"), so the first table shows ana free and bob pro. The second block sorts by updated_at first, so the last row per user is really the newest: ana is "pro" (2026-03-05), bob is "pro" (2026-03-04).

Answers. keep="last" means the last position in the frame. If the rows come in another order tomorrow, for example because the database returns them unordered or a join reshuffled them, the same code returns different plans for the same data, so the result is not deterministic. Sorting by the timestamp (and a tiebreaker if timestamps can tie) before dropping makes the result depend on the data and not on row order. Trap: dedupe on an unsorted frame.
