Simpler, yes, but it can be silently wrong. "First" or "last in the file" means order of arrival, and arrival order is not the order in which things happened. Late events, backfills and retries from a different source can put an old address after a newer one. If I keep the first row, I keep the oldest version, which is the stalest data I have. Nothing fails: I still get one row per customer, so the output looks fine while deliveries and features use outdated addresses. So I sort by the time column and keep the newest row. For ties I use a stable sort, so equal timestamps keep input order and the later row wins, or I add an explicit tiebreaker such as a version number. Rows with a missing timestamp need a decision too, and I would count them and report them rather than let the sort place them silently. Finally, I add a test where the newest row is not the last one in the file, because that is the case that fails silently.
