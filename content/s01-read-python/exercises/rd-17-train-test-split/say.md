The first call splits with test_size=0.3, so the test set gets ceil(10 * 0.3) = 3 rows and the training set the other 7; random_state=42 makes the shuffle repeatable, so every run gives the same rows. The second call adds stratify=y, which keeps the share of positives about equal in both parts. The script prints the sizes, the sorted test rows with their positive count, the same for the stratified split, and whether train plus test together contain every row exactly once.

Answers. 7 and 3 follow from the 0.3 fraction of 10 rows. The seed guarantees the same split on every run on the same library version, not across all versions. Without stratify the split is purely random, so with a rare class the test set can end up with zero positives, and then recall or AUC cannot be computed. With stratify the test set must contain about 20 percent positives; here one of three rows (index 8 is the positive in both splits). The last line prints True: nothing was lost or duplicated.

The trap. Printing "3 rows, 1 positive" for both splits makes them look the same, but the rows differ ([1, 5, 8] versus [3, 6, 8]). The plain split only has a positive in the test set by luck of this seed; the stratified one has it by design.
