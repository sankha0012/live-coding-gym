The clock is a parameter, so the code never reads real time and the tests can move time by hand. I check the deadline before each item, because an item already running should finish and not be left half done. The result is the processed results plus the untouched items, so the caller can retry them in the next run. It is linear in the number of items, with one clock call each. One edge case is the boundary: at exactly the deadline I stop, which means the budget is never exceeded by a new item.
