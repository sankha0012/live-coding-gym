I test the main behaviour first: the k highest, best first. Then the edges where top-k code usually breaks: ties, where I use names out of alphabetical order so a hidden sort by name shows up; k at 0, negative and above the length, because slicing hides off-by-one and negative-index bugs; and the empty list. The last test is a failure path: the function must not sort the caller's list in place, because that would silently change data somewhere else in a pipeline. Each test checks one behaviour, so a failure names the bug.
