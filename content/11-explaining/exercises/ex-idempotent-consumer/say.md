This consumer makes event handling idempotent, so if the broker delivers the same event twice, the handler runs only once. It keeps a set of event ids. For each event it checks the id, skips it if it is known, and otherwise calls the handler and then records the id. Each event costs O(1) on average, and memory grows as O(k) with the number of distinct ids. The risk is the gap between the handler and the seen.add call. If the process crashes there, or the handler raises after it already did part of the work, the event is redelivered and applied again, as the flaky handler in the demo shows with a total of 17. The set also lives in memory, so a restart forgets everything and it grows without limit. In production I would store the ids in a database and write the effect and the id in one transaction, or use a unique key with an upsert, and expire old ids after the broker's redelivery window.
