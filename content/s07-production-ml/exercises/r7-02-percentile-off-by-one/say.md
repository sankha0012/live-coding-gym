The list holds 20 latencies in milliseconds, nineteen of them between 11 and 19 and one outlier of 400. p95_naive sorts the values and takes index int(0.95 * 20) = 19, which is the last element of the sorted list, the maximum, 400. p95_nearest_rank takes ceil(0.95 * 20) - 1 = 18, the 19th value in order, which is 19. The prints are: 20 (the count), 400, 19, and 400 (the max).

Answers. The naive version is off by one: with 0-based indexing, the item at rank r is at index r - 1, so the 95th percentile of 20 values is the 19th value, index 18, not index 19. For small samples this turns p95 into the maximum, so one bad request makes the whole window look like 400 ms when 95 percent of requests were 19 ms or faster. In production that triggers false latency alerts, or erodes trust in the dashboard until real alerts are ignored. The naive index for p50 of 20 values is int(0.5 * 20) = 10, the 11th value, while nearest rank would use index 9, the 10th; they happen to be equal here (14) but would not be in general. The trap is mixing up a rank with an index; the defence is a stated definition (nearest rank here), a test on a tiny known list, and numpy.percentile when interpolation is acceptable.
