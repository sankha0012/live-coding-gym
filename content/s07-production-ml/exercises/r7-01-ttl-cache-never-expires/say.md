The feature store is a dict holding one user's average basket value, the cache is an empty dict and fetches counts real reads. get_features checks whether the user is in the cache; only on a miss does it increment fetches and store a copy of the store entry. The first call misses, caches 42.0 and prints 42.0. Then the store is updated to 55.5. The second call hits the cache, so it returns the old copy and prints 42.0. The third print reads the store directly and shows 55.5. The last line prints "fetches=1 cached=1": the store was read once and one entry sits in the cache.

Answers. The second call prints 42.0 because the cache entry is never invalidated and the copy was taken before the update, so the cache has no way to learn the store changed. In production, a cache without expiry serves stale values for as long as the process lives: a model scoring with weeks-old features, drifting silently away from what training and fresh traffic see, and the cache only grows as new users arrive. The trap is "cache forever". The defence is a time to live: store (value, stored_at) and refetch when now - stored_at exceeds the TTL, plus a size limit. Pass the clock in as a parameter or a function so a test can move time forward without sleeping.
