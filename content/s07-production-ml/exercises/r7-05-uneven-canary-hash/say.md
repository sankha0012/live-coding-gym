in_canary sums the character codes of the user id and keeps users whose sum modulo 100 is under the percentage, here 20. The ids are "u0" to "u999". Character-code sums are a poor hash: ids with the same digits in any order collide, and the sums fall in a narrow range. One-digit ids sum to 165 to 174, two-digit ids to 213 to 231, three-digit ids to 261 to 288, so only the two-digit ids with sums 214 to 219 land below 20 after the modulo. The script prints the count of canary users, 21 (about 2.1 percent, not 20), then the first five, ['u10', 'u11', 'u12', 'u13', 'u14'], then True because the same id always gives the same result.

Answers. A 20 percent canary reaches 21 of 1000 users because the hash is not uniform. In production the canary then sees too little traffic to show a regression, or the wrong kind of users, so a bad model looks fine, or a good one looks bad, and the rollout decision is made on a biased sample. The assignment is deterministic, which is good (a user stays in the same group), but deterministic is not the same as uniform. The defence is a real hash: int(hashlib.sha256(f"{salt}:{user_id}".encode()).hexdigest(), 16) % 100 < percent. Use a salt per experiment so groups do not correlate across experiments, and check the achieved share on real ids. Do not use Python's built-in hash() on strings, which changes between runs.
